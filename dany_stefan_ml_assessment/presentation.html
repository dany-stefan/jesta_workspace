Fixing Fashion Forecasting

From 50% Error to Production-Ready

Dany Stefan | Senior ML Engineer Assessment

February 2026

The Problem

  • 50% WMAPE error in demand forecasting
  • Out-of-Memory (OOM) crashes preventing model execution
  • 12.6M products being forecasted (many inactive or non-replenishable)
  • Footwear category shows worse error than Made-to-Measure

Key Insight: This is not a modeling problem—it's a data engineering problem.

2

Root Causes Identified

  • 1. Dead Stock Noise: Forecasting inactive products that will never sell again
    • Wrong product mix inflates error and wastes compute resources
  • 2. Censored Demand: Zero stock causes zero sales, but doesn't mean zero demand
    • Model learns "no demand" when reality is "could-not-serve demand"
  • 3. Missing Price Features: Model unaware of discounts and clearance events
    • Systematic underprediction during markdown periods

Judgment Call: Tackle data engineering first (dead stock filtering) for quick wins before feature engineering.

3

Our Strategy

Phased Approach: Agile, Modular, Iterative

  • Phase 1 (Month 1): Product Qualification & Data Processing
    • Filter dead stock and inactive products
    • Implement parallel processing to avoid OOM crashes
  • Phase 2 (Month 2): Feature Engineering
    • Address censored demand with stockout features
    • Add price elasticity features for markdown periods
  • Phase 3 (Month 3): Model Optimization & Production
    • Hyperparameter tuning and monitoring setup
    • CI/CD pipeline for deployment

Judgment Call: Fix what's in my domain (data engineering) first—show quick progress before tackling complex ML.

4

Data Insights

Dataset: 100 days, 1 product, 1 store

  • Data Quality Issue: Day 37 had missing sales data
    • Judgment: Safe to fill with 0 since inventory=0 (no sales possible)
    • Confidence: Validated by checking days 36 and 38
  • Illogical Data Points: Sales recorded on same day inventory hits zero
    • Concern: When are sales captured? End of day or beginning?
    • Recommendation: Capture sales at end of previous day to avoid confusion
  • Observable Patterns:
    • Days 41-50: Clear stockout period (inventory=0)
    • Days 70+: Price markdown triggers sales spike
5

Feature Engineering

From 1 Feature → 19 Features

  • Lag Features: 7d, 14d, 28d moving averages (with 1-day shift to prevent leakage)
  • Momentum Features: Sales momentum and stage momentum
  • Inventory Features: Current inventory, 7d/28d trends, momentum
    • Judgment: Inventory proved most important (63% feature importance)
  • Stockout Flag: Binary indicator when inventory=0
  • Lifecycle Stages: New, Growth, Mature, Clearance (one-hot encoded)
  • Price Features: Current price, original price, cost
  • Time Features: Weekday, weeks since launch

Key Insight: Simple lag features underfit regime changes (stockouts, markdowns). Need domain-aware features.

Model Selection

Gradient Boosting Regressor (scikit-learn)

Model Features WMAPE MAE
Baseline (Linear) 1 (28d MA) 110.43% 12.15
Lag Features (GBR) 3 lags 141.33% 15.55
Custom Features (GBR) 19 features 86.94% 9.56

Judgment Call: Used scikit-learn GBR instead of LightGBM due to MacBook compatibility (mobile processor, libomp issues).

Results & Performance

21% Improvement from Baseline to Custom Features

  • WMAPE Reduction: 110.43% → 86.94%
  • MAE Reduction: 12.15 → 9.56 (21% improvement)
  • RMSE: 12.11

Top Feature Importances:

  • Inventory (63.7%): Most predictive feature—stockouts drive demand patterns
  • 28d Inventory Trend (14.3%): Captures replenishment patterns
  • 7d Inventory Trend (5.6%): Recent stock movements matter
  • Weekday (5.2%): Day-of-week seasonality

Key Insight: Inventory features dominate (84% combined). Lag features underfit; domain knowledge beats pure statistics.

Production Design

Product Qualification Module

  • Purpose: Filter out dead stock, inactive, and non-replenishable products before forecasting
  • Architecture: Stateless Lambda function with Polars for data processing
    • Containerized with Docker for easy deployment
    • FastAPI endpoints for API integration
  • Business Rules:
    • Physical stores: 90-day sales lookback, 60-day replenishment window
    • E-commerce: 120-day sales lookback, 90-day replenishment window
    • High-velocity (Footwear): 60-day lookback, 30-day replenishment
    • Low-velocity (Made-to-Measure): 120-day lookback, 90-day replenishment

Judgment Call: Longer windows for e-commerce due to lower storage costs and broader reach.

9

Technical Decisions

  • 1. Polars over Pandas:
    • Why: Faster performance, lower memory footprint, better for 150k SKUs × 61 stores
    • Trade-off: Steeper learning curve, but worth it for scale
  • 2. Gradient Boosting (scikit-learn) over LightGBM:
    • Why: No OS dependencies (MacBook mobile processor compatibility)
    • Trade-off: Slower training, but more portable
  • 3. Time-Series Split (80/20):
    • Why: Avoids data leakage—test on future data only
    • Concern: Small sample size (20 days test), need more data for production
  • 4. Parallel Processing over Cloud ETL:
    • Why: Elegant, reproducible, scalable—hit CPU not memory

Roadmap & Next Steps

If I Had More Time:

  • 1. Larger Dataset: 100 days is too small—need 1-2 years of data for seasonality
  • 2. Cross-Validation: Implement time-series cross-validation for robust evaluation

    • Track false negatives (excluded products that later sell)
    • Track false positives (included products that never sell)
    • Alert on sudden qualification rate changes
  • 6. Real-Time Streaming: Ingest new data continuously for new product launch monitoring
